1. 系统组成与运行依赖

CoreDesk 采用前后端一体化微服务架构，核心后端基于 Python 3.11 与 FastAPI 框架构建，前端由原生响应式 HTML5 / CSS3 / JavaScript 单页应用渲染，不依赖复杂的外部前端编译环境。

服务主体 (FastAPI + Uvicorn)

负责 HTTP API 响应、意图识别与安全决策网关调度、状态流转与前端静态页面分发。

只读账务代理 (CQRS Gateway)

连接核心业务交易库只读镜像，提供账户资产、流水打码量与提现订单状态，避免锁表风险。

知识中台与持久化存储

RAG 规则数据存储于 app/data/faq_knowledge.json，支持热加载更新，无需每次重启服务。

安全决策与后置质检

输入前置过滤 Prompt 注入与敏感词，输出后置执行脱敏与违规承诺核验。

2. 服务器环境与端口规划

根据预估的客服进线量与业务规模，建议按照以下硬件标准进行云服务器配置采购：

部署规格 CPU / 内存 磁盘空间 公网带宽 建议使用场景
测试验证 / POC 1 核 / 2 GB 20 GB SSD 1 ~ 2 Mbps 功能演示、内部联调测试
标准生产配置 2 核 / 4 GB 50 GB SSD 5 Mbps 以上 日常生产环境，500~2000 会话/分钟
大促集群高可用 4 核 / 8 GB 100 GB SSD 10 Mbps 以上 高并发业务高峰，配合 Docker 负载均衡

网络与防火墙端口要求

请确保在云平台安全组（Security Group）及服务器本机防火墙中放行以下端口：

端口号 网络协议 对应服务 访问说明
80 TCP Nginx (HTTP) 面向客户端或坐席浏览器访问，生产中一般重定向到 443
443 TCP Nginx (HTTPS) 生产必须开放，配置 SSL 证书加密通信
8000 TCP CoreDesk 应用端口 若使用 Nginx 反向代理，可仅限 127.0.0.1 内网访问，不对公网开放

3. 方案一：Docker Compose 容器部署 (推荐)

生产环境推荐使用 Docker Compose 进行容器化部署。镜像内已封装完整运行环境，且配置了宿主机数据卷挂载，容器重建或升级镜像时知识库数据不会丢失。

1 安装 Docker 与 Docker Compose 插件
以 Ubuntu / Debian 系统为例，运行以下命令完成基础容器环境准备：
bash 
# 安装 Docker
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
sudo systemctl enable --now docker

# 安装 Docker Compose 插件
sudo apt-get update && sudo apt-get install -y docker-compose-plugin
2 同步代码并进入部署目录
创建生产部署路径（例如 /opt/coredesk）并将代码拉取到该目录：
bash 
sudo mkdir -p /opt/coredesk && sudo chown -R $USER:$USER /opt/coredesk
cd /opt/coredesk
# 将代码克隆或上传至本目录
3 启动容器服务
在包含 docker-compose.yml 的项目根目录下执行构建与后台启动：
bash 
# 启动容器并在后台运行
docker compose up -d --build

# 检查容器状态
docker compose ps
4 检查健康状态与日志输出
bash 
# 跟踪实时日志输出
docker compose logs -f coredesk

日志中显示 Application startup complete 且状态显示 (healthy) 即表示启动成功。此时可通过浏览器访问 http://<服务器公网IP>:8000。

容器数据持久化机制
docker-compose.yml 默认将宿主机的 ./app/data 目录挂载到容器内部。这意味着知识库规则、FAQ 配置均直接保存在宿主机物理磁盘上，重新构建或停止容器不会丢失数据。

4. 方案二：Linux Systemd 守护部署

若服务器不具备 Docker 环境，可使用标准 Python 虚拟环境配合系统级的 Systemd 守护进程运行：

bash - 1. 安装 Python 3 环境与依赖 
sudo apt-get update && sudo apt-get install -y python3 python3-pip python3-venv git
cd /opt/coredesk
python3 -m venv venv
./venv/bin/pip install --upgrade pip
./venv/bin/pip install -r requirements.txt
bash - 2. 注册并启动 systemd 系统服务 
# 复制服务单元文件至系统目录
sudo cp coredesk.service /etc/systemd/system/coredesk.service

# 重载配置并设置开机自启
sudo systemctl daemon-reload
sudo systemctl enable --now coredesk

# 查看运行状态
sudo systemctl status coredesk

5. Nginx 反向代理与 SSL/HTTPS 配置

对外提供正式生产服务时，建议配置 Nginx 作为前置反向代理服务器，处理客户端连接复用、SSL 加密与静态资源缓存：

bash - 复制配置文件并修改域名 
sudo apt-get install -y nginx
sudo cp nginx/coredesk.conf /etc/nginx/conf.d/coredesk.conf

# 编辑配置文件，将 server_name 替换为您实际的域名
sudo nano /etc/nginx/conf.d/coredesk.conf

# 测试配置并重载 Nginx
sudo nginx -t
sudo systemctl reload nginx

申请 Let's Encrypt 免费 SSL 证书

bash 
sudo apt-get install -y certbot python3-certbot-nginx
sudo certbot --nginx -d cs.yourcompany.com

6. 全渠道即时通讯 (IM) 接入配置

系统内置统一 IM 接入网关，支持将 Telegram Bot、Meta WhatsApp Cloud API 与 LINE 官方账号的消息聚合到 CoreDesk 中台统一接待：

即时通讯渠道 服务端 Webhook 路由 协议与验证机制 回发出站目标
Telegram Bot POST /api/webhook/telegram 验证 X-Telegram-Bot-Api-Secret-Token 标头 api.telegram.org/bot<TOKEN>/sendMessage
WhatsApp Cloud API GET / POST /api/webhook/whatsapp GET 握手验证 hub.verify_token；POST 验签 X-Hub-Signature-256 graph.facebook.com/v19.0/<PHONE_ID>/messages
LINE Messaging API POST /api/webhook/line 验证 X-Line-Signature (HMAC-SHA256 Base64) api.line.me/v2/bot/message/reply

账号安全绑定流程 (Account Binding)

第三方渠道首次进线并查询敏感资产（提现、充值、余额、流水）时，为防止非法越权，系统强制执行身份绑定校验：

1 未绑定状态越权查账拦截
若未绑定账号尝试查询个人订单或流水，系统自动阻断并回发绑定引导：“您尚未绑定平台会员账号，请在会员中心获取绑定码，在此回复 /bind <绑定码> 完成关联”。
2 动态指令关联
用户在 Telegram / WhatsApp / LINE 聊天框直接回复 /bind <绑定码>，系统秒级完成双向绑定，后续查询直接打通 CQRS 账务只读数据。

消息防重与幂等处理

第三方平台（特别是 Telegram 和 WhatsApp）在网络抖动或超时后会自动重推同一消息。CoreDesk 网关内置 300 秒滑动窗口幂等集合，对相同 (channel, message_id) 执行自动去重拦截，防止重复回复或重复建单。

7. 运维排查与日常备份

常见问题 1：部署后外网无法访问？
  1. 登录阿里云/腾讯云等控制台，检查当前实例绑定的安全组入方向规则是否放行了 80、443 或 8000 端口；
  2. 在服务器内部执行 curl -I http://127.0.0.1:8000/api/system/mode，若内网能通说明应用正常，问题在于外部网络或防火墙；
  3. 若使用 Ubuntu 系统，请检查 ufw 状态：sudo ufw status，必要时放行端口：sudo ufw allow 80/tcp。
常见问题 2：知识库数据备份与迁移
系统所有的规则库与问答知识位于 app/data/faq_knowledge.json。日常备份只需定期备份该文件或 app/data 目录即可： 
tar -czvf coredesk_backup_$(date +%F).tar.gz app/data/
日志查看指令
  • Docker 部署环境：docker compose logs -f --tail=200 coredesk
  • Systemd 部署环境：sudo journalctl -u coredesk -f -n 200

8. 运行模式机制说明

系统顶部中央设有运行模式切换开关，分为两种工作模式：

运行模式 工作机制 风控安全边界 建议适用时段
Copilot (坐席辅助草稿) 会员进线后，系统生成事实建议草稿展示在坐席输入框上方。草稿不自动发出，由坐席审核或修改后手动点击发送。 由人工坐席承担最终审核责任，系统主要提供事实对齐与规范性话术支持。 新员工上岗、重大版本升级、活动促销高峰及敏感客诉频发时段。
Auto-Pilot (自动驾驶分流) 常规业务咨询（规则、FAQ、无欠额流水）由系统直接答复会员，气泡附带自动应答标识。 高风险硬性拦截：若识别到流水不足、提现卡单或负向客诉，系统阻断直发，强制降级为草稿并生成诊断卡。 日常白班或夜班低人力时段，自动承接标准问题，减轻坐席负担。

9. 实时会话接待与人工接管流程

1 接收进线与意图识别
会员消息进线后，前置安全网关在 1 毫秒内完成意图判别、语言识别与防越狱拦截。
2 查看 AI 草稿与采纳发送
在 Copilot 模式下，输入框上方会浮现 AI 组织的标准回复建议：
  • 点击「采纳并发送」：草稿直接发送给会员；
  • 点击「修改草稿」：草稿自动填入下方输入框，坐席可手工润色后发送。
3 Auto-Pilot 模式下的人工接管
当系统处于自动驾驶模式回复时，若坐席发现需要人工介入，可点击气泡上的「接管会话」或直接在输入框打字发送，系统将平滑转为人工接管状态。

12. 提现卡单与流水异常诊断

出款卡单是客服业务中占比最高的咨询类型。系统将账务计算前置，避免坐席手工核算失误：

流水缺口自动试算规则
当会员咨询“为什么我的提现还没到账”时，系统只读连接账务中台，自动对比：
提现要求流水门槛（例如 ¥50,000） vs 实际已完成打码（例如 ¥45,000） = 流水差额缺口 ¥5,000。

此时工作台左侧将自动唤起【异常事件根因诊断卡】：

  • 诊断信息明确：清晰显示差额 ¥5,000，以及导致卡单的具体充值订单或优惠活动名称。
  • 建议话术指引：提供解释口径，引导会员继续游戏补齐流水，或引导扣除红利。
  • 一键发起工单：若需技术或财务深入排查，点击卡片上的「一键生成工单」，系统自动将订单号、金额与缺口数据带入工单中心。

13. 业务执行中台操作指南 (Action Agent)

坐席可直接在左侧工作区点击快捷功能卡片，处理高频业务闭环，所有操作均记录完整审计日志：

1. 小额掉单核验与补单

规则：单笔充值金额 ≤ ¥2,000 且渠道侧有有效支付流水时，系统自动核验放行，秒级完成上分入账；若金额超过 ¥2,000 则强制转财务复核工单。

2. 提现流水冲正 (扣减红利)

规则：会员流水不足但急需出款时，系统智能试算可扣除的优惠彩金（如扣减 ¥500 红利），坐席确认后解除打码限制，提现单放行出款。

3. VIP 挽留关怀券派发

规则：针对高价值客户因体验不佳产生的客诉，按等级上限派发（VIP 1~2: ¥88, VIP 3~5: ¥288, VIP 6+: ¥888），券码直发会员钱包。

4. 反欺诈与黑灰产检测

规则：一键扫描该账号的 IP 重合度、设备指纹碰撞与套利特征，输出风险评分（正常 / 建议加锁 / 限制出款）。

14. 工单生命周期流转 (Tickets Hub)

点击右侧面板的「工单中心」标签页可查阅工单看板：

工单状态机定义
待审核 (PENDING_REVIEW) → 处理中 (IN_PROGRESS) → 需补足流水 (NEED_TURNOVER) → 已审批出款 (PAYOUT_APPROVED) → 已结案 (RESOLVED)

坐席常用操作：

  • 审核出款：财务或值班主管核对通过后，点击出款按钮，状态变更为已出款；
  • 发放补偿券：因平台原因导致严重延迟的工单，可在工单内直接追加关怀券；
  • 完结工单：输入处置结果说明后点击结案，归档至历史记录。

16. 知识自学习飞轮与影子沙箱 (Phase 5)

系统具备基于坐席真实改动行为的持续学习与迭代机制：

1 草稿修改差分 (Diff) 捕获
当经验丰富的坐席对 AI 提供的草稿进行编辑并发出时，系统后台自动分析修改前后的表达差异。若判定为优质补充，自动提炼并沉淀到候选规则池中。
2 知识库主管一键审批
主管在【知识飞轮与沙箱】页面审查候选规则，点击「采纳入库」，该规则立即热加载注入 RAG 知识库，无需重启服务器。
3 影子评测沙箱验证 (A/B Dual-Run)
在正式上线新规则前，可在沙箱内发起评测。系统并发调用基线模型与候选模型进行双路测试，对比响应延迟、合规得分并给出采纳建议。

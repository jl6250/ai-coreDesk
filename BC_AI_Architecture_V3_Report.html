REPORT / 01

建设目标：可控、可扩展的多语言 AI 客服

以高频咨询自动化和坐席辅助为起点，逐步覆盖业务查询，提升服务效率，同时把身份、权限与业务承诺纳入可审计控制。

效率提升

标准问题直接回答，查询结果自动组织，复杂问题携带摘要转人工。

资金风险控制

只读业务工具、权威事实、审核模板和发送前校验共同建立控制边界。

多站点复用

统一接入与编排，按站点、语言和规则版本配置；各语种独立验收。

推荐路线：先辅助坐席 → 再自动处理低风险问题 → 逐步扩展业务与语种。
首期覆盖后续扩展成功衡量
规则 FAQ、充值/提现状态、人工接管活动资格、流水解释、多语种、成本优化自动解决率、重复咨询率、满意度、关键事实准确性

效率与容量指标在基线数据确定后设定；“零资损”是治理目标，不能作为概率模型的绝对能力承诺。

REPORT / 03

安全闭环：业务事实决定回复边界

入口控制

身份绑定、订单归属、租户隔离；JEV 辅助识别攻击与异常诉求。

执行控制

API 只读、字段白名单；金额、资格、返水与流水由规则服务计算。

出口控制

核对事实与承诺，审核后发送；失败回退模板或人工。

必须落实具体控制失败路径
查询权限服务端绑定用户/站点，验证对象归属拒绝查询或重新认证
业务承诺金额、状态、资格对照权威事实标准模板或人工
知识有效性过滤站点、语言、版本、审批与有效期澄清或人工
流式输出资金与资格类完整审核后发送固定等待提示
接管一致性持久化所有权，接管后暂停机器人工单与明确等待提示
JEV 提供辅助判断，确定性控制建立业务边界。仅拦截“赠金、包赔”等关键词不足以判断错误承诺。
REPORT / 04

典型流程：提现未到账查询

用户身份与意图

确认绑定账号，识别提现查询；必要时追问订单。

授权查询权威状态

校验订单归属，读取状态、更新时间和可公开原因。

组织证据与回复

优先受控模板；LLM 仅使用授权事实和生效 SOP。

发送前审核

核对金额、状态、承诺与敏感信息；通过后发送。

异常与人工处理

接口超时、不明原因或投诉争议，提示无法确认并接管。

留痕与反馈

保存证据引用、策略版本和耗时，人工修正经审核再用于改进。

状态从业务 API 获取；“银行维护”和“到账时间”必须有依据，模型不得自行补充。

受控回复示例：“这笔提现目前仍在处理中，状态更新时间为 {时间}。目前暂无法确认具体到账时间。如需进一步核实，我可以帮您转接客服。”

模板中的状态与时间由接口映射；仅在人工通道可用时提供实时转接，否则创建工单并提示等待。

04 / JEV 决策设计与接入方式

官方文档提供 Choice、Score、Noul 三种原语。多个问题可在单次 API 调用中独立并行评估同一份状态；问题之间不能依赖本次调用的其他答案。复杂策略由代码组合。

决策任务原语输入与处理
意图分类Choice固定候选意图，包含 Other / Need_Clarification；低置信度追问或转人工
注入与规则绕过检测Noul用户消息及必要上下文；按误报与漏报成本校准阈值
情绪强度Score明确有序等级及评分标准；业务优先级再结合系统读取的 VIP 与等待时长
证据支持性检查Noul候选回复、授权事实、允许承诺范围；仅作辅助检测
槽位提取不使用 Choice 作为任意文本提取订单号用正则或表单；时间和复杂字段用结构化生成，再校验
部署基线：JEV 按外部 API 接入。私有化、数据区域、留存政策、限额、并发和 SLA 均待厂商确认；不得据此假设“4 台 CPU 可承载全量”。如生产要求数据不出 VPC，则使用可本地部署的分类模型和规则作为替代，并保持 Adapter 接口不变。
  • 前置输入尽量只包含脱敏消息和必要上下文；后置仅提供经过字段筛选的事实。
  • 每类问题维护 question_version、模型版本、评估集和阈值配置；按语种、意图分别评估。
  • 区分 Noul 的真概率、Choice 的选项概率与 confidence、Score 的评分值；不能统一当作“风险分”。
  • 阈值不固定写死为 0.85；先离线校准，再影子运行和灰度验证。
  • JEV 超时：普通规则走本地分类与标准模板；敏感查询仍需授权校验；关键输出校验不能因降级被跳过。
05 / 接入、身份绑定与会话管理
  • 第三方渠道首次查询个人业务数据前完成账号绑定或安全认证；渠道昵称、手机号文本和订单号不能单独证明身份。
  • 网关生成 trace_id；渠道 message_id 配合 tenant_id、channel_id 做幂等，避免重复查询、重复回复和重复工单。
  • 内部消息保留 channel、locale、authenticated_user_id、tenant_id、site_id、session_id、timestamp；身份与站点字段由服务端可信上下文生成。
  • 会话维护 current_state、slots、evidence_refs、handoff_owner、last_activity、policy_version；超时清理遵循数据保留规则。
  • 人工接管时写入所有权锁和状态版本，停止机器人主动回复；坐席明确释放后才恢复自动模式。
  • 聊天历史与检索内容均视为不可信数据；指令和工具权限不从历史文本中继承。
06 / 对话编排与工具调用策略
状态行为退出条件
RECEIVED鉴权、限流、输入规范化进入决策或拒绝
CLASSIFIED意图与风险判断进入 FAQ、查询、检索、澄清或人工
NEED_SLOT逐步追问必要参数参数有效；超出次数则人工
FETCHING通过工具网关读取事实成功、明确超时或业务错误
DRAFTING模板或证据约束生成产生候选回复
VALIDATING关键字段、PII、授权承诺检查通过发送；失败改模板或人工
HUMAN_OWNED人工处理，AI 仅提供草稿坐席释放或关闭会话
CLOSED归档及质检抽样新问题建立新轮次
  • 路由类别不只 Chat_Gen，应细分充值、提现、活动、账户、游戏规则、投诉等业务意图；多意图问题拆分执行并明确合并顺序。
  • 工具由服务端根据意图和权限选择；LLM 的调用建议必须经过 Schema、白名单和对象归属校验。
  • 为每个请求设置总 deadline、单工具超时和重试上限；仅对可安全重试的查询实施有限重试。
  • 用户主动要求人工、认证失败、事实冲突、投诉争议和高风险账户问题可直接接管；退款诉求应收集事实并按规则升级，不能由模型批准。
  • 超出证据范围时允许回答“目前无法确认”，不强制生成完整答案。
07 / 知识库、RAG 与规则治理
环节实施要求
内容来源客服 SOP、审核后的活动规则、游戏说明和故障公告；记录来源、负责人和审批状态
分块按规则语义边界切分，保留标题、适用条件、例外和引用关系；避免拆开金额与限制条件
过滤字段tenant_id、site_id、business_line、language、jurisdiction、version、effective_from、effective_to、approval_status
检索稠密向量 + 关键词混合检索；候选数量与 Top-K 根据评测调整，Top-3 不作为固定标准
多语言选择支持目标语种的 Embedding 和 Reranker；逐语种验证术语、数字、币种和日期
证据返回 chunk_id、document_id、version、source、有效时间；无足够证据时澄清或人工
发布审核 → 建索引 → 回归 → 灰度 → 发布；支持撤回与缓存失效

Metadata 过滤是逻辑隔离，由服务端强制注入；需要物理隔离的租户使用独立索引、集合或实例。首期可选择支持混合检索的一套存储，是否同时引入 Milvus 和 Elasticsearch 取决于现有平台能力与运维成本。

08 / 业务 API、资金规则与数据一致性

客服读取现有交易系统的权威查询接口，不在客服项目中重建账本、拆分热点账户或改变交易架构。热点查询通过受控读模型、限流和缓存解决，接口必须暴露数据新鲜度。

接口结果字段示例关键约束
QueryWithdrawStatuswithdraw_id、status_code、amount、currency、updated_at、customer_reason_code服务端验证订单归属；内部风控原因不向用户原样披露
QueryDepositStatusdeposit_id、status_code、amount、currency、updated_at禁止凭截图或用户描述确认到账
QueryPromotionEligibilitypromotion_id、rule_version、eligible、public_reason_code、valid_until资格由规则服务计算，不交给 LLM 推断
QueryTurnoverRequirementrequired、completed、remaining、currency、as_of、rule_version使用业务规定的精度与舍入规则
QueryAccountStatusstatus_code、allowed_actions、public_reason_code敏感账户变更转认证流程或人工
  • 所有 API 只读；充值、提现审批、彩金发放和资料变更均不由 Agent 执行。操作引导链接使用允许域名和可信页面配置。
  • 工具结果通过统一事实结构向生成服务提供；异常、无记录、处理中和查询失败是不同结果，不能混淆。
  • 余额、流水与提现状态必须注明来源和 as_of / updated_at；超过业务新鲜度阈值禁止给出确定承诺。
  • 高敏感字段在进入模型前脱敏，最终输出再次检查。金额数值与币种成对校验，避免跨币种表述。
  • 沿用已有 RAM Role / STS 等短期身份机制，密钥由凭证服务管理，不放入 Prompt、日志或代码。
09 / 模型选型、推理与缓存
用途首期建议验证重点
主力生成选择一个可部署的多语言指令模型；Qwen 2.5 14B/32B 可作为候选基线真实客服数据上的证据遵循、语种覆盖、延迟与成本；最终版本以评测冻结
复杂解释先复用主力模型；确有收益再引入高能力模型不让复杂模型替代规则计算；额外成本和数据边界
格式化输出优先代码模板固定状态无需为格式化再部署 7B 模型
推理框架vLLM 或 SGLang 二选一，固定版本批处理、队列、并发、KV Cache 和量化兼容性
量化FP8 或经验证的 AWQ INT4 等配置按具体 GPU 核对兼容；量化后重新评估关键事实准确性
  • 设置最大输入/输出长度、单会话配额、生成超时、队列上限和背压；容量保护基于排队时长与 token 负载。
  • 语义缓存仅用于公开稳定的已审核答案；键包含站点、语言、规则版本与政策版本。规则更新及时失效。
  • 余额、状态、资格使用独立业务缓存，键含授权用户和对象；遵循新鲜度 SLA，禁止跨用户复用。
  • 模型路由不只看 VIP 或情绪，应结合任务难度、数据敏感度、允许区域和服务负载。
  • 如使用外部高阶 API，先明确字段脱敏与出域范围；不将用户身份或账务原文默认外发。
10 / 输出审核、安全与流式发送
检查机制失败处理
金额与币种对照事实字段与代码格式化结果受控模板或人工
业务状态仅允许事实映射中的状态和解释重新查询或提示无法确认
承诺与资格允许承诺范围 + 确定性规则 + JEV 辅助判别阻止发送并回退
敏感数据输入最小化、字段白名单、正则与 NER 补充脱敏；仍不确定则阻止发送
知识与注入来源过滤、指令隔离、工具权限约束忽略恶意指令，必要时澄清
链接允许域名、站点映射和服务器配置移除未知链接
提现、充值、彩金、返水、资格等关键回复：完整生成 → 完整审核 → 发送。审核后可由前端模拟打字效果。未经审核的 token 不能先推送给用户。

普通咨询可按句缓冲审核，但必须评估跨句语义风险；已审核模板直接发送。等待查询时可先发固定提示。第三方渠道采用消息发送与必要的更新机制；不假设具有统一 SSE 能力。

11 / 提现查询端到端示例
  1. 用户询问“提现为什么没到账？”；渠道适配器确认账号绑定并生成 trace_id。
  2. 前置决策识别为提现查询，评估是否存在注入；编排层检查认证与必要槽位。
  3. 服务端获取当前用户订单列表或校验指定订单归属，不使用用户文本指定的 user_id。
  4. 工具网关读取提现状态，返回 PROCESSING、更新时间及可公开原因；若没有“银行维护”依据，则不能编造该解释。
  5. 状态映射器形成事实，例如“该笔提现仍在处理中”；金额、币种和订单尾号由代码填充。
  6. 如需要自然语言解释，LLM 仅使用事实和生效 SOP；不得承诺到账时间。
  7. 输出审核核对字段、承诺和脱敏。通过后发送；失败采用模板或转人工。
  8. 记录证据引用、查询时间、策略版本、审核结果和处理耗时。

模板示例：“查询到您的这笔提现目前仍在处理中，状态更新时间为 {时间}。目前暂无法确认具体到账时间。如果您需要，我可以帮您转接客服进一步核实。”其中时间来自接口，并按站点时区展示。

12 / 部署、安全与容灾

按阿里云现有基础设施落地：公网渠道仅访问入口；编排、知识库、模型和工具网关在私有网络。业务 API 保持私网访问，公网出站通过受控代理。账务接口不因接入客服而放入 DMZ。

  • 服务采用工作负载身份、最小权限和网络访问控制；内部按实际能力实施 mTLS。GPU 推理服务独立资源池和访问策略。
  • Redis 高可用保存短期状态，持久化存储保存接管与审计；知识文档、索引与模型配置有版本和备份。
  • 多可用区部署无状态服务；是否配置 GPU 跨区冗余根据 RTO/RPO 与成本评估，不能只凭多副本宣称容灾。
  • 日志记录 trace_id、model_version、question_version、policy_version、tool_call、evidence_refs 和 guardrail_result；原始 PII 默认不落日志。
  • 定义数据保留、权限审计、知识发布权限和回滚流程；模型输出和人工修正不能未经审核直接进入知识库。
异常降级路径必须保留的控制
LLM 排队或故障FAQ 模板、查询状态模板、人工鉴权与输出校验
JEV 超时或不可用本地规则/分类、低风险模板、人工工具权限和确定性承诺检查
RAG 不可用已审核固定答案；其余人工不依赖模型记忆回答活动规则
业务 API 超时提示暂时无法查询，工单或人工不返回缓存过期状态冒充当前状态
坐席不可用工单与可见等待提示不能宣称已实时转接
全链路故障独立静态通知/人工联系方式预先验证兜底通道可用
13 / 容量测算与性能预算

容量按入口请求、生成占比、token 长度与在途请求计算。以下仅为测算示例，不能直接推导 GPU 采购数量。

参数假设值推导
入口峰值1000 请求/秒明确为用户消息，不等于同时在线会话

平均输入长度1500 tokens输入需求约 30 万 tokens/秒
平均输出长度200 tokens输出需求约 4 万 tokens/秒
平均生成时间4 秒稳定负载下约 800 个在途生成请求
JEV 调用次数前置 1 次；20% 请求后置 1 次约 1200 API 调用/秒；问题数与计费另核算

GPU 数量须用选定模型、硬件、量化、上下文长度和真实并发压测，测出满足延迟目标时的吞吐；加入故障冗余、流量突增和运维余量。大规模张量并行不是默认最优方案，应比较多副本与不同并行度。

16 / 核心数据契约示例

以下为内部建议契约，并非 JEV 官方请求格式。生产接口应通过 JSON Schema 校验，身份字段由网关提供。

MessageEnvelope {
  trace_id, session_id, channel_message_id,
  channel, locale, tenant_id, site_id,
  authenticated_user_id, user_text, received_at

  injection_probability, emotion_score,
  question_version, model_version, latency_ms
}
EvidenceBundle {
  evidence_id, source_type, source_version,
  retrieved_at, as_of, freshness_status,

ReplyCandidate {

  passed, deterministic_checks, semantic_checks,

对话编排必须拒绝无证据引用的关键业务陈述；审核通过结果与对应候选文本绑定，避免审核后文本被修改。
